# Riff Battle — описание проекта и требования

Версия документа: **1.0**. Основание: лабораторная работа № 2. Статус «уже есть» означает, что сценарий доступен пользователю через интерфейс; если готов только HTTP API, указано «нужно доработать». Номера FR, NFR и US закреплены за описанными возможностями.

## 1. О приложении

Riff Battle — веб-приложение для коротких музыкальных баттлов: участники входят в комнату, получают общий барабанный луп, сочиняют рифф, слушают работы без подписей авторов, голосуют и видят результат. **Гость** играет по нику без регистрации. **Владелец аккаунта** входит по почте и паролю и может вести профиль. **Хост** — участник, создавший комнату или получивший эту роль после явного выхода предыдущего хоста; он запускает раунд. Закрытие вкладки само по себе не считается выходом и не меняет хоста.

**Комната** объединяет игроков и настройки баттла; публичная видна в списке, приватная доступна по коду. **Раунд** — один цикл сочинения, голосования и результатов. **Луп** — общая барабанная запись с заданными BPM и числом тактов. **Рифф** — партия из нот и тембра, сохранённая участником в раунде. **Голос** — выбор одного чужого риффа. **Профиль** — имя, псевдоним, статистика и история владельца аккаунта.

На начало работы уже действуют HTTP API для регистрации, гостевого входа, комнат, раундов, риффов, голосования и профиля; сервер хранит игровые данные в PostgreSQL, сессии — в Redis. API восстановления пароля реализован, но требует настройки SMTP. Есть страницы главной, входа, комнат, лобби, голосования, результатов и профиля. Большинство игровых страниц используют демонстрационные данные и ещё не подключены к API; редактор Piano Roll и полноценный сквозной игровой путь отсутствуют. Состояние отдельных возможностей указано ниже.

Сервер выдаёт токен сессии сроком на 7 суток. Для целевого интерфейса токен хранится в `sessionStorage` текущей вкладки: обновление страницы сохраняет вход, закрытие вкладки удаляет токен из браузера. При загрузке страницы интерфейс проверяет токен через `GET /api/v1/session/me`; истёкший или отозванный токен не даёт доступа. Это выбранное правило хранения для будущей реализации frontend, а не описание уже работающего механизма.

## 2. Требования

Приоритеты: **обязательно** — до конца семестра, **желательно** — при наличии времени, **потом** — вне текущего объёма. Признак выполнения описывает поведение в интерфейсе, а не только наличие маршрута API.

**Граница FR-8:** минимум три участника устраняют однозначное раскрытие чужого автора, характерное для игры вдвоём. Но отсутствие подписи и идентификатора автора до результатов всё равно не гарантирует, что личность нельзя установить косвенно. Проверку сокрытия полей можно считать выполненной для API; FR-8 целиком остаётся «нужно доработать», пока интерфейс не подключён к API и не обеспечивает голосование.

## 3. Пользовательские сценарии

Каждый сценарий описывает целевое поведение приложения. Если шаг пока работает только через API, его реализация в интерфейсе входит в соответствующее требование.

### US-1 — гостевой вход (FR-1)
Я как гость имею ник длиной 2–24 символа, ввожу его в форму входа и подтверждаю. Получаю гостевую сессию и список комнат. Вход: ник. Выход: токен на 7 суток на сервере, сохранённый в `sessionStorage` вкладки, отображённый ник и доступ к комнатам. После обновления той же вкладки интерфейс проверяет токен через `/session/me`; слишком короткий или длинный ник отклоняется без создания игрока.

### US-2 — регистрация и вход (FR-2)
Я как новый игрок имею почту и пароль длиной 8–72 символа, открываю регистрацию, ввожу данные, затем вхожу в аккаунт. Получаю сессию владельца аккаунта. Вход: почта, необязательное уникальное имя пользователя, ник длиной 2–24 символа и пароль. Выход: созданный аккаунт, токен на 7 суток в `sessionStorage` вкладки и доступ к профилю. Занятое явно указанное имя пользователя возвращает 409 `{"code":"conflict","detail":"Такое имя уже занято"}`; аккаунт не создаётся. Пароль вне диапазона отклоняется проверкой входных данных.

### US-3 — восстановление доступа (FR-3)
Я как владелец аккаунта имею доступ к своей почте, запрашиваю восстановление, открываю ссылку из письма и задаю новый пароль. Получаю возможность войти с новым паролем. Вход: почта, одноразовый токен из ссылки, новый пароль. Выход: подтверждение смены пароля; токен погашен. Требуется настроенный SMTP и страница подтверждения сброса.

### US-4 — поиск или вход по коду (FR-4)
Я как игрок с действующей сессией открываю список публичных комнат либо ввожу код приглашения, выбираю доступную комнату и вхожу. Получаю лобби с текущими участниками. Вход: сессия и, для приватной комнаты, код комнаты. Выход: членство только в одной комнате и её актуальный состав. Во время сочинения и голосования вход закрыт; сначала нужно явно выйти из другой комнаты.

**Пример:** участник с действующей сессией вводит код `ABCD23` существующей комнаты с одним свободным местом; `POST /api/v1/rooms/join` с телом `{"code":"ABCD23"}` возвращает 200 и объект комнаты, где поле `code` равно `"ABCD23"`, а `members` содержит нового участника. Если ввести несуществующий код `ZZZZ99`, ответ — 404 с полным телом `{"code":"not_found","detail":"Комната не найдена"}`; членство не создаётся. При попытке войти в другую комнату ответ — 409 `{"code":"conflict","detail":"Сначала выйдите из текущей комнаты"}`. Во время активного раунда — 409 `{"code":"conflict","detail":"Раунд уже идёт, войти нельзя"}`. Интерфейс показывает `detail`. Поле `code` в запросе и успешном ответе — **код комнаты**, а поле `code` в теле ошибки — **код ошибки**.

### US-5 — создание комнаты (FR-5)
Я как игрок с действующей сессией указываю название, видимость, число мест и длину лупа, создаю комнату. Получаю лобби и роль хоста. Вход: сессия, имя, `public`/`private`, вместимость 3–6, 4 или 8 тактов. Выход: идентификатор и код комнаты, сохранённые настройки, список участников с хостом. Если игрок уже состоит в другой комнате, создание отклоняется. При явном выходе хоста следующий по времени входа участник становится хостом; закрытие вкладки такого эффекта не имеет.

### US-6 — начало раунда (FR-6)
Я как хост комнаты с минимум тремя участниками выбираю луп или оставляю выбор пустым и запускаю раунд. Получаю общий луп, BPM и время окончания сочинения и голосования. Вход: сессия хоста, идентификатор комнаты, необязательный `loop_id`. Если он не задан, сервер выбирает первый луп каталога подходящей комнате длины. Выход: новый раунд со стадией `composing`, дедлайном сочинения через 5 минут и дедлайном голосования через 10 минут после старта. Интерфейс вычисляет обратный отсчёт по `server_now` из ответа и серверным дедлайнам; изменение часов компьютера не меняет оставшееся время.

**Пример:** хост комнаты с тремя игроками выбирает `blast-155-8`; запрос `POST /api/v1/rooms/{room_id}/rounds` с `{"loop_id":"blast-155-8"}` возвращает 201, `stage="composing"`, `loop_id="blast-155-8"`, `bpm=155`, `bars=8`, `composing_ends_at` через 300 секунд и `voting_ends_at` через 600 секунд после `composing_started_at`. Если в комнате только два игрока, ответ 409 с телом `{"code":"conflict","detail":"Нужны минимум три игрока"}`; раунд не создаётся. Если запрос отправляет участник, не являющийся хостом, ответ 403 `{"code":"forbidden","detail":"Запустить раунд может только хост"}`. Интерфейс показывает `detail`.

### US-7 — создание риффа (FR-7)
Я как участник раунда в течение пяти минут сочинения выбираю тембр, добавляю ноты, прослушиваю партию и сохраняю её. Получаю сохранённый рифф, доступный для повторного редактирования до дедлайна. Вход: сессия, идентификатор раунда, тембр и ноты (`pitch`, `start`, `duration`, `velocity`). Выход: идентификатор риффа и сохранённые ноты; по истечении пяти минут сохранение отклоняется.

### US-8 — голосование без подписей авторов (FR-8)
Я как участник раунда в течение пяти минут голосования прослушиваю работы без имён авторов и выбираю один чужой рифф. Получаю подтверждение выбранной работы. Вход: сессия, идентификаторы раунда и чужого риффа; свой рифф для голосования необязателен. Выход: сохранённый голос и `your_vote_riff_id` в состоянии раунда. Даже если все проголосовали раньше, результаты появляются лишь после `voting_ends_at`; после дедлайна голос не принимается.

**Пример:** участник выбирает чужой рифф с UUID `11111111-1111-4111-8111-111111111111`; `POST /api/v1/rounds/{round_id}/votes` с телом `{"riff_id":"11111111-1111-4111-8111-111111111111"}` возвращает 201 и полное тело `{"riff_id":"11111111-1111-4111-8111-111111111111"}`. Если указать UUID собственного риффа, API возвращает 403 с полным телом `{"code":"forbidden","detail":"Нельзя голосовать за свой рифф"}`; голос не создаётся. Интерфейс показывает `detail`.

### US-9 — просмотр результатов (FR-9)
Я как участник завершённого раунда открываю результаты. Получаю список авторов, число голосов за каждый рифф и победителей. Вход: сессия и идентификатор раунда после `voting_ends_at`. Выход: `stage="results"`, опубликованные авторы, голоса и `winner_ids`; при нуле голосов каждый сохранённый рифф входит в `winner_ids`, а если риффов вообще нет, список победителей пуст.

### US-10 — профиль (FR-10)
Я как владелец аккаунта открываю профиль, просматриваю статистику и историю, меняю имя и псевдоним. Получаю сохранённый профиль. Вход: сессия аккаунта, новые `name` и `handle`. Выход: обновлённые поля, число завершённых баттлов и история раундов.

Стадии раунда вычисляются сервером по времени: `composing_ends_at` наступает через 300 секунд после старта, `voting_ends_at` — ещё через 300 секунд. Ошибки последовательностей соответствуют текущему API; сообщения в интерфейсе являются требованием к доработке frontend.
