# Лабораторная работа № 1 «Запуск проекта»

**Проект:** Riff Battle.
**Выполнили:** Пинаев О.К., Соболев Д.Р.

## Цель работы

Выбрать программный проект на семестр, описать его предметную область,
подготовить репозиторий и среду разработки, разобрать структуру приложения,
оценить технические риски и составить план последующих работ.

## 1. Выбор проекта

Для разработки выбран Riff Battle — веб-платформа музыкальных соревнований.
Участники получают общий барабанный луп и за пять минут создают гитарный рифф
во встроенном Piano Roll. Затем работы прослушиваются анонимно, участники
голосуют и получают результаты раунда.

Проект создан с нуля. Beat Battle использован как ориентир игровой механики;
разработка собственного редактора и музыкального сценария составляет
предметную область Riff Battle.

Целевая аудитория — гитаристы, начинающие авторы музыки и компании друзей,
которым нужен короткий музыкальный челлендж без внешней DAW.

Выделены две роли: участник и хост комнаты. Хост обладает правами участника
и дополнительно создаёт комнату и запускает раунд. Для участия предусмотрены
два способа входа: гостевой по нику и через аккаунт. Регистрация включена
в текущую версию, но необязательна для игрока.

Определены пять основных сущностей: игрок/идентичность, комната, раунд, рифф
и голос. Карта включает десять пользовательских функций, объединённых
в три направления: организация баттла, создание риффа и определение результатов.

Подготовлен [паспорт проекта](../00-project.md) с описанием функций,
технологического стека, состава команды и распределения работы.

## 3. Среда разработки и запуск

Для приложений заданы следующие версии инструментов:

| Инструмент | Версия |
| --- | --- |
| Node.js | 24 в CI и Docker, локальный минимум 22.18 |
| pnpm | 10.14.0 |
| Python | 3.12 в CI и Docker, локальный минимум 3.12 |
| uv | 0.8.18 в CI и Docker |
| PostgreSQL | 17 |
| Redis | 8 |

Подготовлены два многостадийных Dockerfile. В финальных образах приложения
запускаются от пользователя `app` с UID/GID `10001`. Compose определяет
healthcheck, порядок готовности сервисов и постоянные тома PostgreSQL и Redis.

### Воспроизведение запуска

В каталоге версии репозитория, содержащей исходники и `compose.yaml`, выполнить:

```sh
docker compose up --build --wait --wait-timeout 180
python scripts/smoke-compose.py
```

Для запуска нужны Docker Engine в режиме Linux containers и Compose v2
с поддержкой `--wait`. Python на хосте используется для smoke-скрипта.

| Компонент | Адрес |
| --- | --- |
| Стартовая страница | http://localhost:3000 |
| Документация API | http://localhost:8000/docs |
| Liveness endpoint | http://localhost:8000/api/v1/health |

Ручной сценарий проверки состоит из трёх шагов:

1. Открыть стартовую страницу и проверить отображение `pe-backend: ok`.
   Ответ `/api/v1/health` — `{"status":"ok","service":"pe-backend"}`.
2. Изменить значение демонстрационного счётчика и сохранить локальную заметку.
   Интерфейс отображает новое значение и подтверждает запись в IndexedDB.
3. Проверить состояние сервисов через `docker compose ps`; smoke-скрипт
   проверяет HTTP API, серверный рендеринг и загрузку ресурсов страницы.

Для остановки с сохранением данных используется `docker compose down`.
Ключ `-v` удаляет тома и применяется только при намеренном сбросе окружения.

## 4. Разбор структуры приложения

### Frontend

Frontend построен на React, TypeScript и TanStack Start. Использована FSD-структура
с направлением зависимостей `app → pages → widgets → features → entities → shared`.
Настроены алиасы слоёв, публичные API слайсов и автоматическая проверка импортов.

TanStack Query управляет серверными данными, Zustand — состоянием интерфейса,
Dexie — локальным хранением в IndexedDB. Для стилей используются SCSS Modules.
Точка входа `frontend/src/router.tsx` передаёт создание маршрутизатора
в `app/router.tsx`; маршруты расположены в `app/routes`.

### Backend

Backend построен на FastAPI. В `api` находятся HTTP-обработчики,
в `schemas` — транспортные модели, в `services` — сценарии приложения,
в `domain` — доменные модели, в `infrastructure` — место для адаптеров хранения.
Конфигурация вынесена в `core`, приложение собирается в `main.py`.

Проверочный endpoint демонстрирует взаимодействие слоёв:
`GET /api/v1/health → HealthService → HealthStatus → HealthResponse`.

### Данные и конфигурация

PostgreSQL и Redis включены в инфраструктурный состав проекта. В текущем
каркасе соединения приложения с ними ещё не реализованы. IndexedDB используется
демонстрационной функцией записи заметки.

Адрес API браузера задаётся через `VITE_API_URL`, внутренний адрес для SSR —
через `API_INTERNAL_URL`. Backend получает настройки с префиксом `PE_`.
В Compose параметры передаются через окружение; для локальной разработки
предусмотрены `.env.example`.

### Карта функций

В [паспорте](../00-project.md#3-карта-функций-и-объём-семестра) составлена карта
десяти функций: способы входа, создание и посещение комнаты, запуск раунда,
редактор, тембр и воспроизведение, фиксация риффа, прослушивание, голосование,
результаты и повторная игра. Для каждой функции указаны целевые модули
и ручной сценарий проверки.

В соответствии с заданием для нового проекта игровые функции отмечены
как планируемые. Результат первой работы — подготовленный скелет разработки;
реализация игрового цикла отнесена к последующим этапам.

## 5. Инженерные практики и выявленные вопросы

Настроены линтеры, проверка типов, тесты, production-сборки и автоматизация CI.
Общий workflow вызывает проверки обоих приложений и интеграционный запуск
Compose, а итоговый check `CI` объединяет их результаты.

При разборе проекта выделены три ключевых вопроса:

1. Выполнимость браузерного аудио: запуск AudioContext, задержки, загрузка сэмплов
   и синхронность гитары с барабанным лупом.
2. Серверное управление раундом: дедлайн, фиксация работы, восстановление сессии,
   связь гостя с аккаунтом и защита голосования от повторных действий.
3. Подтверждение происхождения и условий распространения гитарных сэмплов
   и барабанных записей.

Для их учёта подготовлены [тексты issue product и трёх вопросов](issues.md).
Таблица [состояния инженерных практик](../00-project.md#состояние-практик)
включена в паспорт.
